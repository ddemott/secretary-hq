## 2026-06-25 — Beth go-live: "calls don't log" + "Beth freezes mid-call"

A multi-hour debugging marathon taking the voice agent (Beth, Thinking Hammer) from "nothing works on a real call" to "logs everything + holds a conversation." Two distinct problems, conflated for a long time.

### The two problems (don't conflate symptoms)

1. **"Nothing logs."** Calls connected but the dashboard showed nothing / stale `active` rows.
2. **"Beth freezes."** She greets, answers a turn or two, then goes silent; caller hangs up.

These looked like one bug ("calls are broken") and got conflated. They were separate, with separate root causes. **Lesson: when two symptoms co-occur, explicitly separate them before theorizing — a single "it's broken" frame hid that logging and the conversation were failing for unrelated reasons.**

### Root causes (what was actually wrong)

- **Logging:**
  - `voice_sessions.caller_phone` was `NOT NULL`, but forwarded-line/anonymous callers have no caller ID → `start_voice_session()` threw → no row. (Fixed: column nullable.)
  - The agent finalized the call only in `ctx.addShutdownCallback`, which fires on **JOB_SHUTDOWN** — but the LiveKit worker stays alive between calls, so a single hangup never shut the job down → `voice-session-end` was **never called** (proven: `tool_calls_total{tool="voice-session-end"} = 0`). Rows sat `active` forever. (Fixed: finalize on the session **`Close`** event, which fires on participant disconnect; reaper as backstop.)
  - The transcript was only written at finalize → a call that hung lost its transcript. (Fixed: persist the transcript-so-far after **every turn**.)
  - The dashboard polled only *active* calls, never history/detail → a finalized call kept showing stale `active / 0:00 / no transcript` until manual reload. **This caused most of the false "nothing logged" reports.** (Fixed: auto-refresh history + selected call.)

- **The freeze (the real one):** **OpenAI TTS latency.** Direct timing settled it — `gpt-4o-mini` LLM = ~1s, but OpenAI **TTS (tts-1) = 2–5s per sentence**, and the `@livekit/agents-plugin-openai` TTS does **not stream** — observable behavior: no audio plays until the whole clip is synthesized (verified by reading the installed package: `super(..., { streaming: false })` and `stream()` throws). So every reply had a multi-second silent gap; the caller said "hello?" into the gap, which **completed a new turn during the in-flight generation and discarded the reply** (trace: `playout interrupted, playbackPositionInS=0`, `function call missing the corresponding function output, ignoring`). (**Fixed in PR #98**: switched the TTS model to `gpt-4o-mini-tts` ~1.3s + raised interruption `minWords` 0→2 / `minDuration` 500→800ms so a 1-word backchannel can't discard the reply. Planned: pre-rendered/cached TTS for routine lines.)

### Meta-lessons (the expensive ones)

- **MEASURE before "fixing" a latency/perf problem.** I guessed the freeze cause wrong ~5 times (turn-detection, stuck-speaking, speakFiller deadlock, LLM hang, rate-limiting) and shipped fixes for several before the actual cause. The breakthrough was a **2-minute direct timing test** (curl OpenAI LLM vs TTS) that showed LLM fast / TTS slow. One measurement beat hours of theorizing.
- **Don't blind-patch when you can't see.** Each speculative fix that "should" have worked but didn't cost a full CI+deploy+retest cycle. A wrong fix isn't free — it consumes the user's next test.
- **Anchoring is the enemy.** I latched onto "intermittent TTS stall" and walked past cheaper discriminators (the caller had given a *partial* phone number; the DB showed 0 customers saved). Re-derive from the evidence each round; don't defend the prior hypothesis.
- **Sad paths must be instrumented or you debug blind.** The call-finalize was fire-and-forget with a single swallowed `warn`; when it failed there was *no trace*. Rule (now standing): every fire-and-forget / best-effort path that can fail silently emits a **metric** (survives log truncation) + a 5W log naming the cause (SQLSTATE, status, payload). This is what finally made calls diagnosable.
- **Get the real trace before committing to a fix.** Hours were lost theorizing because I couldn't read the agent's turn-state. Once the trace was in hand (`agent_state_changed`, `user_input_transcribed`, `function_tools_executed`), the cause was obvious in minutes. Instrument first, then read, then fix.

### Observability gotchas (how to actually see prod)

- **Metrics survive truncation; logs don't.** Prometheus `/metrics` (gated by `METRICS_TOKEN`, direct curl to the backend) gave hard facts (`voice-session-start`=1, `voice-session-end`=0) when Railway log retention truncated to ~40 lines. Lean on counters for "did X happen, how often."
- **Railway's management GraphQL API rate-limits a team token hard** under heavy use (deploy-watch + log polling) — it stayed throttled for *hours*, blocking log reads entirely. Don't build your only observability path on it. Alternatives that bypass it: the **Railway dashboard UI**, `railway logs --service <svc>` in a logged-in terminal, the app's own `/metrics`, querying the prod **DB directly**, and **Sentry/Better Stack** if a DSN/token is set on the service (the agent had neither — set them).
- **Prod DB is a first-class debugging tool.** Reading `voice_sessions` directly (transcript, status, duration) + running the reaper RPC against prod proved the logging path end-to-end without any logs.

### LiveKit Agents (Node) specifics learned

(All "specifics" below are behaviors of the **`@livekit/agents`** packages — inspect them under `agent/node_modules/@livekit/agents*`, not this repo's source.)

- `ctx.addShutdownCallback` runs on **job shutdown**, not per-call. A reused worker doesn't shut down between calls → use the session **`Close`** event (`CloseReason.PARTICIPANT_DISCONNECTED`) to run per-call teardown.
- `ToolsClient.call()` (this repo, `agent/src/toolsClient.ts`) **resolves `{ ok:false, status }` on 5xx/401 — it does NOT throw.** A bare `.catch()` won't catch a backend failure; inspect `res.ok`.
- The `@livekit/agents-plugin-openai` **TTS does not stream** (package source: `super(..., { streaming:false })`; `stream()` throws). Audio only plays after the full clip synthesizes → model latency = dead air. (The old Grok plugin was also non-streaming.)
- `@livekit/agents` internals (`dist/voice/agent_activity.js`): `userTurnCompleted()` **skips the reply** (logs `"skipping user input, current speech generation cannot be interrupted"`) when current speech isn't interruptible; a new short user turn during in-flight generation can orphan a function-call output.
- `turnHandling.interruption` defaults: `minWords: 0`, `minDuration: 500` → *any* sound (even "hello?") counts as an interruption. Raise them so backchannels don't cancel a reply.
- Calling `session.say()` from **inside** a tool's `execute()` (the old `speakFiller`) is an unsupported pattern — avoid it. (It turned out not to be the freeze cause, but it's still wrong.)

### Process / tooling gotchas

- **`git push` is slow because the pre-push hook runs the full quality suite** (`scripts/example-pre-push-hook.sh` → `npm test`), which needs the **local test DB on :5433**. When that DB isn't up, the hook fails locally even though the code is fine. Use `git push --no-verify` (CI is the authoritative gate) when the DB isn't running.
- **Branch protection requires the branch be up-to-date with main** before merge (`mergeStateStatus: BEHIND` blocks). Merge `origin/main` into the PR branch + push when other PRs land first.
- **Every Copilot review pass caught at least one real bug** (the `res.ok` vs throw handling, the empty-transcript wipe, the negative-age reaper window finalizing live calls, search_path/REVOKE on the SECURITY DEFINER fn, zero-width chars in comments). Adversarial review before merge earned its keep — don't rubber-stamp; verify, fix, resolve.
- **merge-before-migrate**: apply the prod DB migration before merging code that reads the new shape (or make the code forward-compatible). A SECURITY DEFINER maintenance function must pin `search_path` and `REVOKE EXECUTE` from `PUBLIC` + Supabase `anon`/`authenticated`.
- **Recover a deleted/closed PR's branch** with `git fetch origin refs/pull/<N>/head` — no "Restore branch" click needed.
- **`setup-db.sh` silently no-ops through the Supabase pooler when a migration self-manages transactions.** The runner applies each file with `psql --single-transaction` **and** appends its own `INSERT INTO schema_migrations`. Migration files that carry their **own `BEGIN`/`COMMIT`** (e.g. `20260607000001_booking_buffer_enforcement.sql`) collide with that wrapper — you see both `WARNING: there is already a transaction in progress` (the file's `BEGIN`) and `WARNING: there is no transaction in progress` (the wrapper's trailing `COMMIT`). Against a **direct** localhost/CI Postgres it happens to commit (CI stays green); against the **Supabase pooler** it reported `APPLY` / `RC=0` while **nothing durably committed** (column absent, `schema_migrations` unchanged). Fix: for prod/pooler, apply the migration files **directly** — `psql "$PROD_URL" -v ON_ERROR_STOP=1 --single-transaction -f <file>` (let the file's own `BEGIN/COMMIT` do the work) + a separate `INSERT ... ON CONFLICT DO NOTHING` into `schema_migrations`. Then **verify against the DB**, never trust the runner's summary. (2026-07-01, buffer migration.)
- **Two mocks facing each other test nothing.** The landing page's "Try live demo" button returned `400 Invalid JSON` in production for its entire life, while `/demo/start` was healthy the whole time. The dashboard's `fetch()` declared `Content-Type: application/json` and passed **no body**; `JSON.parse('')` threw inside `jsonContentTypeParser` before the route ran. Both suites were green: `demo-route.test.ts` used `app.inject()` with no `payload` (Fastify sets no content-type → the JSON parser is skipped) **and** built a bare `Fastify()` with the *default* parser rather than the production one, while `page.test.tsx` stubbed `fetch` outright. Neither side ever constructed the one request shape the browser actually sends. Two lessons: (1) when a suite mocks the transport, it must at minimum **assert the request shape** it's promising the other side; (2) a route test that registers its own content-type parser is testing a parser **prod never runs** — register the real one (`removeContentTypeParser` first, for built-in types). The bug's whole surface lived in the gap between the two mocks. Empty body now parses as `{}` (matching `express.json()`); malformed JSON still 400s. (2026-07-08.)
- **A mount-once provider makes `router.push` a silent session-loss bug.** After the demo-button 400 was fixed, `/demo` still landed on the **login screen**: `/demo/start` returned 200 and wrote the session to `localStorage`, then `router.push('/dashboard')` ran. But `SessionProvider` sits in the **root layout** and reads `localStorage` in a mount-once `useEffect(…, [])`. A client-side push never remounts it, so it kept its initial `tenantId = null`, and `app/dashboard/page.tsx` gates on exactly that → `<LoginView/>`. `LoginView` itself works only because it calls `setTenantId` directly. Rule: **any route that writes the session from outside React state must navigate with a hard load** (`window.location.href`), or the provider must subscribe to `storage` events. The unit test could not catch it — it mocked `next/navigation`, so `push` was a spy with no router behind it, and jsdom has no real navigation. Only driving the deployed page in a real browser exposed it. (2026-07-08.)
- **Retract a root cause the moment the evidence dies.** During the same investigation I concluded the `/demo/start` per-IP limiter was a *global* bucket (429s persisting past the 15-min window; a spoofed `X-Forwarded-For` landing in the same bucket) and wrote that into two docs. A controlled **16-minute quiet-window test returned 200** — the window resets fine; the 429s were my own accumulated test traffic, and the spoof failed because Railway *overwrites* `X-Forwarded-For` with the true client IP (correct, non-spoofable). Two lessons: when you are the one generating load, **your own traffic is a confound** — measure from a quiet baseline before theorizing; and a plausible mechanism plus correlated symptoms is not a root cause until one controlled test could have falsified it. (2026-07-08.)
- **Never judge a command's success through a pipe.** `npx vitest run 2>&1 | tail` / `| grep` reports **`tail`/`grep`'s** exit code, not the command's — a failing suite looks green. This burned an hour: an "exit 0" full-suite run was actually `tail` succeeding while 3 tests failed underneath, sending me hunting a phantom regression that was really a **drifted local `test_db`** (missing `persona_name`/`default_service_id` because an earlier `db:migrate` had stopped on a pre-existing idempotency error). Always capture the real code: `cmd > /tmp/out.log 2>&1; echo "EXIT=$?"` or check `${PIPESTATUS[0]}`. And when local tests fail but CI is green, **suspect test_db drift first** — rebuild it CI-identical (drop → `setup-db.sh` full chain → `seed-db.sh`) before touching code. (2026-07-01.)

- **"1012 passed" and a nonzero exit are not a contradiction.** `npm run prepare-commit` reported step 2 failed while vitest printed `Tests 1012 passed (1012)` — the failure was `Errors 2 errors`, two **unhandled rejections** attributed to no test. Cause: `dashboard/lib/hooks.ts` fired its fetch from `useEffect` with no cancellation, so when a component unmounted mid-flight the `setLoading(false)` continuation ran after vitest tore down jsdom; React's `dispatchSetState → requestUpdateLane → getCurrentEventPriority` reads `window` unconditionally and threw `ReferenceError: window is not defined`. Three traps: (1) it **only reproduced under full-suite load** — the file passed 3/3 in isolation, because the race needs teardown to beat the fetch; (2) a naive regression test (unmount, then resolve) **passes with or without the fix**, since setState-after-unmount is a silent no-op while `window` still exists — the test must `delete globalThis.window` to simulate teardown before resolving; (3) the fix must be proven **both ways** — a mounted-guard that always returned early would make the SAD tests pass while silently breaking every list view, so keep a HAPPY test asserting data still lands. Fixed with a `useIsMounted()` ref guarding every post-`await` setter. (2026-07-09.)
- **A pre-commit gate that cries wolf gets ignored.** The same `prepare-commit` run had been red on a pristine `main` for two independent reasons, neither of which was code: `eval "$cmd"` leaked the `cd dashboard` from `checks`/`unitTests` into the parent shell (stranding every later step → `Missing script: "verify:claude-md"`), and the focused-test scan's `(\.only\(|\.skip\()` regex flagged all 12 legitimate **conditional** skips (`test.skip(process.env.FOO !== '1', …)`, `ctx.skip()`) as focused tests. A gate that fails regardless of code state trains everyone to skip it, so the one real signal it later produced (the unhandled rejections above) had been sitting unread. Run each config command in a subshell; discriminate a *disabled* test (`.skip('name', …)` — first arg is a string literal) from a *guarded* one (first arg is an expression). (2026-07-09.)

- **An unverified gate is indistinguishable from a broken one.** Two in one day. (1) CI's `dorny/paths-filter` had a `code` filter ending in `'!**/*.md'`; dorny feeds that array to picomatch, where **a negation in an array matches every file that isn't markdown** — so `.gitignore`, `LICENSE` and `workflow.config.json` all matched, and the docs/config-only skip had *never* worked for anything but `.md`. It looked right in the YAML for weeks. Fixed in #226 by dropping the negation (over-runs = safe; the exact `'src/**/!(*.md)'` extglob tested clean locally but would skip E2E on real code if dorny's picomatch lacked extglob — wrong failure direction). (2) `docs/planning/TODO.md` asserted branch protection worked because the rule was *configured*; nobody had watched it stop a red PR. PR #227 pushed a deliberately-failing test: `Backend` red → `BLOCKED` → `gh pr merge` refused (`the base branch policy prohibits the merge`); deleting the test → `CLEAN` → merge allowed. Both halves now observed, not assumed. Corollary: **guards must fail safe.** The CI step guards were `code == 'true' || event != 'pull_request'`, so an empty output from a broken filter *skipped* the suite; now `code != 'false'`, so anything unexpected runs. And never put a job-level `if:` on a required check — a job that skips never *reports*, and branch protection then blocks the PR forever waiting on it. (2026-07-09.)

- **A set-but-invalid credential passes every presence check you own.** Prod's `TELNYX_PHONE_NUMBER` held `+16308661960` — a number whose Telnyx order had been **deleted**. It is the outbound-SMS `from` fallback (`tenantConfig.inboundPhone || process.env.TELNYX_PHONE_NUMBER`), so every tenant without its own `inbound_phone` was sending confirmations and reminders from a number Telnyx no longer owns: provider rejects, silent `status='failed'` rows in `communications_history`, nothing raised. Three reasons it survived: (1) `featureReadiness.ts` asserts the var is **set**, never that it is **owned** — a dead value reads as healthy; (2) **inbound voice was unaffected**, because call routing is Telnyx-number → SIP-Connection and never touches this var, so the 2026-06-30 live-call test passed while SMS was broken — a green test on an adjacent path; (3) the P1 item "verify reminder delivery stats in prod" had never been run, and it was the only thing that would have shown it. Corollary on config layers: **tenant** config lives in the DB and is hot (change `tenants.tts_voice` and the next call uses it — `fetchTenantConfig` runs per-call with no cache), while **platform** config lives in env and needs a redeploy. A Railway variable edit is staged until you click Deploy; until then the running process still holds the old value — the same "build without restart is a no-op" trap, one layer up. (2026-07-09.)

### Durability principle (reinforced by Dale)

A record must exist **from the start of the call**, keyed by something stable (call_id/timestamp), **independent of whether name/phone are collected or the agent finishes cleanly.** Layer it: write at start → enrich incrementally (transcript per turn) → finalize on hangup → server-side **reaper** backstop for anything that still slips through. The dashboard must **auto-refresh** so the durable record is actually *visible* without a manual reload.

- **A `waitFor` anchored on text that renders WITHOUT the awaited work is not a wait.** PR #274 (agent-only diff, zero dashboard files) failed CI's Dashboard job on `BillingView` "shows active plan name": the test's `waitFor` targeted `/^growth$/i`, which the STATIC plan card matches before the mocked billing API resolves — so the wait could pass instantly and the follow-up `getByText('Active')` (which DOES depend on the API) raced the fetch. Green locally for weeks; red on a slower CI runner. Two rules: (1) anchor `waitFor` on text that only the awaited state change can produce — waiting on the thing under test, not on scenery; (2) when CI fails on a branch whose diff cannot plausibly cause it, go hunting for a latent race or time-bomb in the TEST before suspecting the diff — rerunning until green just re-arms the trap for the next PR. (2026-07-17.)

- **`rebuild-db.sh` defaults to the `postgres` database; vitest uses `test_db` — know which DB each tool touches before diagnosing "the seed is empty."** One night, three self-inflicted mysteries in a row: (1) a sim run failed "no open slot in 8 days" and the first diagnosis blamed vitest pre-push runs resetting the DB — but those hit `test_db`, not the backend's DB; (2) psql checks then "confirmed" an empty seed — by querying `test_db` while the backend served `postgres`; (3) the REAL cause was neither: the seed is bare-bones **by design** (2026-05-18), so a freshly rebuilt DB has NO services/employees/shifts anywhere, and `sim-taskgroup` requires a pre-configured bookable `SIM_TENANT`. Every wrong turn came from not pinning down which database each tool reads before theorizing. Restore path for the sim tenant: copy the business shape from prod read-only (`\copy` employees/resources/tenant_skills/services/service_employee/service_resource/employee_schedule + the tenants config columns, in FK order, with explicit column lists — column ORDER differs between DBs whose migration chains ran at different times). (2026-07-17.)

- **The suggest layer and the enforce layer must read the same CLOCK — not just the same grid.** Evening of the same day as the quarter-hour-grid fix, its sibling: `available-slots` offered a caller 1:00 PM Monday while a `scheduled` appointment sat exactly there; booking's GiST correctly refused (`TIMESLOT_OCCUPIED`) and the model silently rebooked 2:45. Two stacked timezone bugs: (1) the SQL cast `start_time::text` rendered the `timestamptz` in the SESSION timezone — UTC on the Supabase pooler — while shift coverage is local `TIME` columns, so the 1:00 PM booking became "18:00", fell outside the 13:00–17:00 window, and subtracted nothing; (2) the JS helper `dateTimeToMinutes` ran `new Date(dt).getHours()`, which renders in the SERVER's timezone (UTC on Railway) — so even a correct fetch would have been read on the wrong clock. Fix: render appointments tenant-local in SQL (`AT TIME ZONE t.timezone`, on the date filter too — else late-evening local bookings file under the wrong UTC day) and parse bare local times with `timeToMinutes`. Verified by replaying the live scenario against a local backend: book 1:00 PM via the production RPC → the slots list immediately excludes it. Family rule (now two members): whenever a SUGGEST path and an ENFORCE path both reason about time, diff their grid origin AND their clock — they were written at different times by different hands, and each disagreement is a caller being offered something booking will refuse. (2026-07-17.)

## 2026-07-20/21 — Question-tree live-call loop: seven calls, every bug a pattern

An overnight build-test-fix loop on the checklist architecture (branch `feat/question-tree-architecture`): Dale test-calls, reports symptoms in a sentence, the transcript+worker-log+DB triangulate the cause, the fix ships with a test, repeat. The bugs sorted into five reusable patterns.

### Pattern 1 — The promotion ladder: a prompt rule the model breaks twice becomes host code

Symptoms, in sequence: dictated numbers went unconfirmed on two consecutive calls despite a strengthened prompt rule; the caller's name was heard once and never used; the model ran a full job intake past a ready `book` action ("you just blew right past that") even though the tracker rendered booking first; "what would you like to discuss?" after the opener named the topic, three calls running. Every one had a prompt rule against it. **A prompt rule is a request; the tool result is an instruction.** Fixes, all host-side in `checklistTools.ts`: the `record_answer` result now carries the exact 3-3-4 read-back string when a ten-digit number is recorded; carries a use-their-first-name nudge when the name is recorded; every state block ends with a `NEXT:` pointer naming the first frontier item ("an ACTION, not a question. Do it now"); and (pending) `set_purpose` auto-records `meeting_topic` when booking + a subject tree are co-selected. Rule of thumb: the model reliably obeys the LAST tool result; it unreliably obeys paragraph 4 of the system prompt.

### Pattern 2 — Host directives must be conditional, or they cause the bug they fix

The READ-BACK-NOW directive (pattern 1's first fix) produced a **double read-back** the same day: the model read the number back on its own, got a yes, THEN obeyed the directive and read it back again — two "Yeah. That's right." in a row. An unconditional imperative in a tool result is obeyed even when already satisfied. Directives must be idempotent: "if you have not already read it back and heard a yes…".

### Pattern 3 — Watchdog vs the speech queue: state transitions lie when two audios share one 'speaking'

Two stomps, two orderings, same root: the dead-air watchdog's disarm logic keyed off agent-state TRANSITIONS, but the speech queue serializes filler and reply into ONE continuous `speaking` span — no second transition ever comes. (a) Filler-first: reply queued behind the still-playing filler → the "a later 'speaking' disarms" event never fires → recovery line played OVER the live slot offer. Fix: on the filler's done-callback, wait a 300ms settle beat — still `speaking` means that audio IS the reply → disarm. (b) Reply-first: the reply's SpeechHandle joins the queue ~300ms before its audio starts (state still `thinking`), the filler fired inside that window and queued BEHIND it — caller heard question + "Just a moment." + recovery run together ("you're running all these sentences together"). Fix: probe `session.activity.currentSpeech`/`speechQueue` before speaking a hold (skip if anything is scheduled — audio imminent), and at the recovery deadline treat `speaking` as proof of live output (the ~1.2s filler cannot still be playing 4s on): stand down and `interrupt()` the stray queued filler. Both timelines are replayed in `watchdog.test.ts`. Meta: the worker log's event timeline (`agent_state_changed` + `watchdog_hold_played` timestamps) made both orderings legible in minutes — the same instrument-first lesson as the Beth freeze.

### Pattern 4 — VAD endpointing is boxed in from both sides; a fixed threshold cannot win

550→900→1300ms, each raise bought by a real mid-number cutoff. Then 1800 (the fourth raise) LIVELOCKED the very next call: the caller finishes a sentence, waits ~1s, hears silence (VAD still counting), assumes he wasn't heard, resumes — resetting the counter. His re-speak reflex (~1–1.5s) is SHORTER than the threshold, so no turn could EVER commit: 13s of speech, 14 STT fragments, zero response, hang-up. A threshold above the caller's own patience is not "patient", it is deaf. Reverted to 1300 = the documented ceiling: below ~1300 it cuts off number-recall pauses (recoverable — "seems you got cut off"); above ~1500 it livelocks (unrecoverable). The real fix is semantic/content-aware endpointing (Deepgram end-of-utterance or LiveKit's turn-detector plugin — neither installed yet).

### Pattern 5 — One value, four schemas: enum drift bounces the whole write mid-call

A live caller answered "contract to hire." The checklist tree accepted it (its options included `contract_to_hire`) — but the backend Zod enum knew only `contract|full_time`, so it rejected the ENTIRE capture; the agent re-interrogated the caller and finally mislabeled the role "contract". Same value passes through four independently-owned shapes: tree options → agent tool schema → host backfill map (which was silently COLLAPSING contract_to_hire→contract to fit the backend) → backend Zod → DB column. They had three different vocabularies. Fix: contract_to_hire first-class end to end, tested at the outermost seam (realdb: the row stores the verbatim value). Siblings caught the same night: the model spoke the raw token ("do you mean contract_to_hire?" — underscores, out loud; style rule: record tokens, speak words) and the backend's spoken string full-named the owner ("passed along to Dale DeMott"; first-name-only at every speakable seam).

### Singles worth keeping

- **Never tear down the machinery a tool stands on from inside its `execute()`** — the router lesson's family grows: `updateTools()` inside a router tool (07-20) and now `session.close()` inside `finish_call`'s goodbye (the teardown killed the tool's own task → every clean close logged "An internal error occurred"). Defer both to a macrotask.
- **Unit-proven ≠ obeyed.** The tracker's book-first walk order had a passing positional unit test while the live model ignored the rendering entirely. The E2E tier (`sim-questiontree.ts`, live LLM caller vs real prompt/tools, snapshot-graded) caught it on its first run — then earned its keep again by exposing run-to-run selection flake ("I have a position to run past Dale" → message tree, not job). Tool-order instrumentation (`toolOrder`) turned "book FIRST" from a vibe into a grader.
- **The E2E replay scenario IS the regression log**: DALE'S CALL in sim-questiontree encodes every reported defect of the week as a grader (slots-before-capture, one read-back, name used, no re-asked topic). A reported symptom that doesn't become a grader will be re-reported.

---

- **`DROP SCHEMA public CASCADE` takes `api_user`'s grants with it — a baseline rebuild leaves every realdb test 500ing.** Roles are cluster-wide and survive the rebuild, so `SELECT rolname` says api_user is fine; the GRANTs were schema-scoped and are gone. This was the actual root of the day's local mysteries (293 backend failures after a rebuild, then 6/6 realdb 500s blamed on "env drift"): the app pool connects as api_user and every query failed on permissions. Remedy: re-apply the grants block from `20260228000003_api_user.sql` after any baseline rebuild (candidate improvement: rebuild-db.sh should do this itself). Corollary caught the same hour: a timezone bug pair can CANCEL on a dev machine whose OS timezone equals the tenant's (SQL renders UTC, JS re-reads server-local) — pin `process.env.TZ='UTC'` in tests that guard timezone rendering, or the test only fails where you aren't looking. The constraint failure was loud enough to mask it entirely. The three pieces — enum, gate, stale release — only work together, and each is commented as such at its own site. (2026-08-19.)


- **The migrator said `APPLIED=0 SKIPPED=185 FAILED=0` and that is what success looks like when it has done nothing at all.** PR #355 shipped `20260820000000_employee_schedule_pattern.sql` and, being a table the new code READS, had to reach prod before the merge. Dale ran `npm run db:migrate` against the prod URL and reported it applied. It had not been: prod's newest applied migration was still `20260819000000`, and `select count(*) from information_schema.tables where table_name='employee_schedule_pattern'` returned **0**. The cause is that `db:migrate` can only apply **what is on disk in the current checkout**, and the migration lived on the feature branch while the shell was on `main` — so the runner walked 185 files instead of 186, found nothing new, and printed a clean summary. There is no error, no warning, and no mention of the file that is missing; the only tell is the COUNT. Then it happened a second time, to me, on the first retry — same cause, same convincing output. Four lessons: (1) **verify a migration by querying the TARGET DATABASE, never by reading the migrator's summary** — the summary describes the files it saw, not the schema you now have; (2) **`git checkout` the branch carrying the migration first**, which is easy to forget precisely because the house rule says migrations go in *before* the merge, i.e. at a moment when `main` cannot contain the file; (3) **a zero-work success is more dangerous than a failure** — a permission error would have announced itself, and this is the same family as Telnyx's false "sent" and the `outcome='message'` that promised a row nobody wrote: the mechanism worked, the report was true about the wrong thing; (4) **confirm you are on the database you think you are** before concluding a migration failed — the check that made this diagnosable was `current_database()` plus two known-recent artifacts (`tenant_question_trees` present, the reminder `'sending'` constraint live), which ruled out "wrong DB" before anyone started debugging the runner. Post-fix verification is now the standard: table present, PK shape, `relrowsecurity`/`relforcerowsecurity`, policy names, trigger name, row count — read back out of prod. (2026-08-20.)
